# 家庭 AI 食谱推荐系统｜项目实施规划

> 版本：v1.0（2026-09-25）
> 依据：项目整合规划.md（原始需求）、需求技术方案选型(2).md（技术方案）、需求业务规则补全方案(3).md（业务规则）、标准 Python-FastAPI 项目工程结构.md（工程规范）
> 原则：本规划仅编排实施路线与验收标准，不进入编码；编码在规划确认后按阶段启动。

---

## 一、规划总览

系统为前后端分离网页应用：Vue3 + Element-Plus 前端，Python FastAPI 后端，MySQL 8.0 + Redis 缓存，外部 AI 能力（大模型 / 多模态 OCR / 方言 ASR），后端 Docker + 前端 Nginx 部署。

主流程闭环：**家庭档案 → 食材录入 → AI 食谱生成 → 采购建议 → 用户反馈 → 周营养报告**。

一期目标：主流程全链路跑通（档案 / 食材 / 食谱 / 采购 / 反馈 / 周报）。
二期预留：舌苔体质识别、买菜渠道对接、食材消耗自动扣减、采购天数可配置。

## 二、阶段划分与依赖关系

```
阶段0 源码就位与现状核验
   │
   ▼
阶段1 工程脚手架初始化 ────────────► 阶段2 数据库与营养基础数据（可并行）
   │                                    │
   ▼                                    ▼
阶段3 后端分层骨架与通用能力 ◄──────────┘
   │
   ├──► 阶段4 家庭档案模块（阻塞修复，优先）
   ├──► 阶段5 食材录入模块
   │
   ▼
阶段6 AI 食谱生成引擎（依赖：档案 + 食材 + 营养数据 + 大模型密钥）
   │
   ├──► 阶段7 智能采购清单（依赖：引擎营养缺口输出）
   └──► 阶段8 反馈与周报（依赖：引擎食谱记录 + 反馈录入）
   │
   ▼
阶段9 前端页面开发（可与阶段4-8 后端接口并行开发）
   │
   ▼
阶段10 联调、测试与部署
```

**执行顺序原则**：
- 阶段 0 → 1 → 2 → 3 严格串行（脚手架、库表、骨架互为前提）。
- 阶段 2（建库 + 导入营养数据）与阶段 3（后端骨架）可并行推进。
- 阶段 4（档案）与阶段 5（食材）可并行；两者都是阶段 6 的输入，必须先行完成并验证。
- 阶段 6 完成后，阶段 7、8 可并行。
- 阶段 9 前端开发在接口契约（schemas）确定后可提前并行，不阻塞后端。

## 三、分阶段详细规划

### 阶段 0：源码就位与现状核验（前置阻塞项）

- **现状**：当前工作区 `D:\code\Home_Flavor` 为空目录，无任何现有网页代码；"家庭档案存储 BUG" 的修复对象不在工作区。
- **任务**：
  1. 用户提供现有网页版源码或确认源码路径，放入工作区。
  2. 核对现有代码技术栈（是否可复用前端页面 / 后端逻辑）。
  3. 定位档案保存失败根因（提交未 insert/update 的代码路径），形成修复方案。
- **验收**：现有代码可在工作区访问，修复方案明确到具体文件与改动点。

### 阶段 1：工程脚手架初始化

- **任务**：按《标准 Python-FastAPI 项目工程结构.md》搭建目录骨架：
  - 根目录：`README.md`、`CHANGELOG.md`、`LICENSE`、`.gitignore`、`requirements.txt`、`startup.py`、`.env` / `.env.example`
  - `src/` 下建 `config / controllers / schemas / models / services / repository / clients / utils / exceptions`
  - `resources/dict`（同义词字典、初始化数据）、`resources/init_data`（食物成分表、DRIs 源文件）
  - `tests/`（conftest、test_service、test_controller、test_utils）、`docs/`
- **关键约定**：业务逻辑只在 service；数据库操作只在 repository；第三方调用只在 clients；常量集中在 `config/constants.py`；密钥只进 `.env`。
- **验收**：`python startup.py` 可启动 FastAPI 空服务，`/docs` 可访问；`pytest tests/ -v` 可执行（空集通过）。

### 阶段 2：数据库建设与营养基础数据导入

- **任务**：
  1. 建立 MySQL 库（如 `ai_recipe`），按《需求技术方案选型》第七节建 8 张表：
     - `family`、`family_member`（含 `is_deleted`）、`household_ingredient`（含 `available_weight`、`weight_unit`）、`recipe_generation_record`、`user_feedback`、`weekly_nut_report`、`food_nutrition`、`dris_standard`
  2. 导入《中国食物成分表》与《中国居民膳食营养素参考摄入量 DRIs》基础数据。
  3. 建立食材同义词映射字典（如 鸡蛋/土鸡蛋）。
  4. 确认 `@app.on_event` / lifespan 初始化逻辑（表结构校验、字典校验）。
- **验收**：8 张表现库可查；food_nutrition 与 dris_standard 数据完整可查询；weights / 单位字段对齐业务规则文档。

### 阶段 3：后端分层骨架与通用能力

- **任务**：
  1. `config/settings.py` 读取 `.env`；`config/constants.py` 定义业务常量（核心营养素集合、采购天数=3、成员上限=8、缺口触发阈值=30%、超标阈值=1.2×RNI 等）。
  2. `exceptions/`：自定义业务异常 + 全局异常处理器，注册到 app。
  3. `repository/db_session.py` 会话管理；各 repo CRUD 骨架。
  4. `utils/`：`weight_parser`（"番茄 500g"拆分）、`synonym_util`（同义词合并）、`excel_export`（导出 xlsx/csv）、`date_util`（周统计窗口）。
  5. `clients/`：`llm_client`、`multimodal_client`、`asr_client` 的接口封装骨架（先 mock，密钥就绪后接通）。
- **验收**：分层调用链（controller→service→repository）跑通一个示例（如健康检查接口）；异常处理器生效；utils 单测通过；clients 可用 mock 注入。

### 阶段 4：家庭档案模块（阻塞修复，一期最高优先）

- **任务**：
  1. 修复档案存储 BUG：`family_member` 提交后正确 insert/update 落库，生成食谱时可读取。
  2. `models/schemas`：member 校验按《业务规则补全方案》第四节字段枚举 + 年龄 0–120（0 表婴儿，允许小数）+ 姓名≤20 字符。
  3. 成员上限 8 人，超出提示"最多添加 8 位家庭成员"。
  4. 删除采用逻辑删除 `is_deleted`：前端不展示、新食谱不读取、历史食谱/反馈/周报 JSON 保留、不再参与新周报统计；禁止物理删除。
  5. 接口：成员增删改查（list/add/update/delete（逻辑））。
- **验收**：新增成员后查库有数据；再次编辑 update 生效；删除后列表不展示且历史记录可查；生成食谱接口能读到成员档案。

### 阶段 5：食材录入模块

- **任务**：
  1. 三种录入方式：拍照识别（multimodal client）、文字输入（weight_parser 拆名称+重量）、武汉方言语音（ASR client，方言场景，可先普通话降级）。
  2. 三种方式识别结果都走**人工确认兜底**：展示识别列表 → 用户删错补漏、可改重量 → 点【确认食材】后才入库。
  3. 字段：名称必填 + 重量选填（`available_weight` + `weight_unit` 默认 g），支持仅名称 / 名称+重量两套逻辑。
  4. 接口：食材列表增删改、清空（标记失效 `is_valid=0` 而非物理删）。
  5. **一期不做用量消耗自动扣减**，食材由用户手动维护。
- **验收**：三种录入均可入库并可在 UI 确认；文字输入"番茄 500g"正确拆分为名称+重量；仅名称模式不触发重量相关计算；同义词可合并展示。

### 阶段 6：AI 食谱生成引擎（核心模块）

- **任务**：
  1. 组装 Prompt：成员档案（年龄/性别/目标/体质/慢病/过敏/忌口）+ 当前食材 + 约束规则（优先用现有食材、输出共享菜品+分餐+摄入优点+营养缺口、参考 DRIs、缺口>30% 输出采购清单）。
  2. 强制 JSON schema 输出；后端解析 JSON（不解析自由文本）。
  3. 菜品来源混合模式：优先自建菜谱库（MySQL，含菜名/主要食材/烹饪方式/营养参考值/食材配比），匹配不到由模型生成。
  4. 过滤逻辑：过敏原食材、忌口、孕妈/辅食等目标在 Prompt 与后端双重过滤。
  5. **两层营养校验**：模型粗评 JSON → 后端用 food_nutrition 表按分餐分量本地重算实际摄入 → 对比 DRIs 修正缺口 → 输出最终结果。
  6. 超时控制：LLM 调用 30s 超时，超时提示"生成食谱超时，请减少食材或稍后重试"。
  7. 生成记录落 `recipe_generation_record`（输入食材、共享菜品、分餐方案、采购清单 JSON）。
- **验收**：给定档案+食材可稳定返回并落库结构化结果；JSON schema 校验通过率（含重试后）≥ 95%；本地营养二次校验能修正明显的模型数值偏差；过敏原自动过滤生效。

### 阶段 7：智能采购清单

- **任务**：
  1. 触发条件（按《业务规则补全》第二节）：家庭**任意一名成员**任一核心营养素（蛋白质、钙、铁、锌、维生素A、维生素C）缺口占比 > 30%，或本次主菜数量 < 2 道 → 触发。
  2. 计算口径：采购量 = 全员 DRIs 日推荐值 × 3 天（一期固定 3 天）− 已有食材可供给量；未填重量的食材不扣减，仅标记"家中已有，优先消耗"。
  3. 合并规则：同一种食材只出现一行，叠加总克数；按 P0（缺口最大成员核心营养素食材）→ P1（性价比家常食材）→ P2（小众食材）排序。
  4. 导出 Excel（csv/xlsx）：字段顺序 优先级 / 食材名称 / 需要补充营养素 / 建议采购量(g) / 备注。
  5. 展示规则：已有未填重量 → 保留行 + 备注【家中已有，建议评估存量后采购】；已有且填重量 → 扣减后 ≤ 0 则移除。
- **验收**：构造增量测试用例（缺口>30% 触发、主菜<2 触发、未填重量不扣减、扣减后移除）全部通过；导出文件字段与顺序正确。

### 阶段 8：反馈与周度营养报告

- **任务**：
  1. 反馈录入：勾选实际做的菜 + 每位成员实际食用分量（g）；支持【一键全选】（复用 AI 分餐分量）；手动输入优先。
  2. 折算链路：`user_feedback` → 菜品食材配比分解（自建菜谱库）→ 查 food_nutrition 累加 → 单餐单成员营养 → 按天聚合 → 按周聚合（周一~周日）。
  3. 无反馈日期**不估算、不补数据、不参与统计**；周基准 = RNI × 有效记录天数。
  4. 周报输出：达标率、累计缺口、超标项（实际摄入 > 1.2×RNI 标记超标）；problem_summary + 下周建议。
  5. 生成模式：手动生成 + 每周日自动生成（`generate_type` 0/1）；已逻辑删除成员不参与新周报统计。
- **验收**：单餐→天→周聚合数据链路可追溯；无记录日不污染统计；一键全选与手动分量结果一致；周报字段完整。

### 阶段 9：前端页面开发（Vue3 + Element-Plus）

- **任务**：按接口契约开发页面：
  1. 家庭/成员档案管理页（增删改、枚举选择、上限 8 提示、删除确认）
  2. 食材管理页（拍照/文字/语音三入口 + 识别结果确认列表 + 重量编辑 + 手动增删）
  3. 食谱生成页（触发生成、三层结果展示：共享菜品 / 个人分餐+双维度营养评估 / 采购清单）+ 采购清单导出
  4. 反馈录入页（勾选菜品 + 分量 + 一键全选）
  5. 周报页（周度营养报告展示）
- **验收**：五个页面与后端接口联调通过；识别确认、导出、一键全选等交互符合业务规则；响应式基础布局可用。

### 阶段 10：联调、测试与部署

- **任务**：
  1. 全链路联调：档案 → 食材 → 生成 → 采购 → 反馈 → 周报。
  2. 补测试：service 单测（营养/采购/档案）、controller 集成测试（mock 外部 client）、utils 测试；覆盖业务规则边界。
  3. Dockerfile + docker-compose（后端环境）；前端构建产物 Nginx 托管配置。
  4. 文档落位：`docs/api.md`、`business_rules.md`、`tech_architecture.md`、`database_design.md`；README 补齐启动/配置/测试说明；CHANGELOG 记录。
- **验收**：`pytest tests/ -v` 全绿；本地 Docker 一键启动前后端可访问；文档与实现一致。

### 二期预留（不在一期排期）

- 舌苔 / 体质图像识别（体质档案自动填充）
- 买菜渠道对接（美团买菜等，采购清单一键下单）
- 食材消耗自动扣减、采购天数可配置、多家庭 / 账号体系
- 方言识别能力增强（武汉话专项优化）

## 四、全局前置条件（编码前必须确认）

1. 大模型 API 密钥（可选通义千问 / 豆包，需支持 JSON 输出）
2. 多模态 OCR 密钥（豆包多模态 / 通义千问多模态）
3. ASR 方言语音密钥（火山语音 / 阿里云，确认是否支持武汉话/湖北方言场景）

5. MySQL 8.0 本地 / 远程实例可用
6. 现有网页版源码就位（阶段 0）

> 密钥只进 `.env`（本地）与部署环境变量，禁止入 git、禁止硬编码。

## 五、一期最终验收检查清单

1. 新增家庭成员数据库 `family_member` 正常写入、更新；生成食谱可读取成员数据（阻塞 BUG 修复验证）
2. 食材录入 `household_ingredient` 正常写入；三种录入方式均带人工确认
3. 营养缺口计算：6 种核心营养素、缺口占比公式、>30% 或主菜<2 触发采购，后端本地计算为准
4. 采购清单：3 天口径、同类合并、P0/P1/P2 排序、导出 Excel 字段正确
5. 反馈→周报：菜品→食材分解→按天→按周聚合；无记录日不估算；超标阈值 1.2×RNI 生效
6. 成员上限 8 人、字段枚举校验、逻辑删除且历史数据可查
7. LLM 调用超时 30s 有降级提示；JSON 解析异常有兜底
8. `pytest tests/ -v` 全绿；docker-compose 一键启动成功
